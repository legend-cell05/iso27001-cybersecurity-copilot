A GRC tool is easy to write and hard to trust. This one is built around the
parts that decide whether anybody should: a **control catalogue as versioned,
fingerprinted data**, a **risk register where a residual score has to be earned
by an implemented control**, **evidence that expires**, **22 finding rules that
each name themselves**, and an **audit-readiness gate that refuses with exit
code 3** and prints the number that refused it.

No language model is involved anywhere. Every finding is reproducible, and
every finding can be argued with — which is the only kind a security manager
will act on.

> ### ⚠️ Synthetic data, no deployment, and no text of the standard
>
> **Meridian Logistics SAS does not exist.** Every asset, risk, control
> decision, acceptance and evidence record is generated by `sentinel demo`.
> Nothing here has been deployed.
>
> The catalogue references ISO/IEC 27001:2022 control and clause
> **identifiers**; every title, intent and evidence rule in it is written for
> this project. **No text from the standard is reproduced** — see
> [`docs/catalogue.md`](docs/catalogue.md). Using this for a real certification
> still requires a licensed copy of ISO/IEC 27001 and ISO/IEC 27002.

## The problem

An organisation preparing for ISO 27001 certification keeps its ISMS in
spreadsheets: a Statement of Applicability tab, a risk register tab, a folder
of evidence, and a calendar reminder for the internal audit. Every one of those
is individually reasonable. Together they fail in four specific ways, and this
project exists to catch each of them.

**The SoA has a hole in it.** Ninety-three controls, and one of them was never
decided about. The row is simply absent, so nothing looks wrong — until the
auditor works down the list.

**The register is a plan reported as a state.** Every risk shows a comfortable
residual score, because the treatment was entered when it was agreed. The
controls it rests on are still "planned". The register says 43% of the risk is
gone; the organisation has not moved.

**A signature covers a number that changed.** A risk was accepted at a residual
score of 4. The quarterly review re-scored it to 8. The acceptance is in a
different file and nobody looked at it. The risk is now, formally, unaccepted.

**Annex A is not the certificate.** Ninety-three implemented controls and no
management review is a failed stage 2 audit, and a tool that tracks only Annex
A will report everything as fine.

---

## Objectives

- One catalogue, versioned and fingerprinted, that an assessment can prove it
  used.
- Findings that are deterministic, named, and carry what to do about them.
- A residual risk number that cannot be claimed without the control behind it.
- Evidence that ages, at a rate that depends on what kind of evidence it is.
- A gate that can refuse, with a number, and an override that is recorded
  rather than routed around.
- A Statement of Applicability built by walking the catalogue, so that what is
  missing appears in the document.
- Every claim in this README reproducible with the commands in section 10.

## Architecture

```
  catalogue/ (versioned YAML, read-only in the image)     PostgreSQL schema `isms`
  ┌────────────────────────────────┐              ┌────────────────────────────────┐
  │ 93 controls, 25 requirements   │              │ asset · risk · risk_control    │
  │ evidence kinds + freshness     │              │ risk_acceptance                │
  │ closed vocabularies            │              │ control_state  ← the SoA       │
  └──────────────┬─────────────────┘              │ requirement_state · evidence   │
                 │ SHA-256 fingerprint            │ management_activity            │
                 ▼                                └───────────────┬────────────────┘
        ┌──────────────────────────────────────────────┐          │ read once
        │ RegisterSnapshot -- all a rule may look at   │◀─────────┘
        └──────────────┬───────────────────────────────┘
                       ▼
        ┌──────────────────────────────┐   ┌────────────────────────────┐
        │ 22 finding rules (pure)      │──▶│ finding                    │
        └──────────────┬───────────────┘   └────────────────────────────┘
                       ▼
        ┌──────────────────────────────┐   ┌────────────────────────────┐
        │ readiness gate, 7 checks     │──▶│ assessment · readiness_check│
        └──────────────┬───────────────┘   └────────────────────────────┘
                       ▼
        ┌──────────────────────────────────────────────────────────────┐
        │ SoA (md + csv) · treatment plan · findings · audit dossier    │
        │ each hashed and recorded against the assessment              │
        └──────────────────────────────────────────────────────────────┘
```

The rules read a snapshot and cannot query. That constraint is why they are
testable without a database, why the CLI and the API cannot disagree, and why
an assessment is a single consistent read. Full reasoning in
[`docs/architecture.md`](docs/architecture.md); the decisions and their costs in
[`docs/decisions.md`](docs/decisions.md) (18 ADRs).

## Tech stack

| Layer | Choice | Why this one |
| --- | --- | --- |
| Language | Python 3.11+ | typed throughout, `mypy --strict` clean |
| Storage | PostgreSQL 16 | the invariants that matter are `CHECK` constraints and a partial unique index, not application code |
| Catalogue | YAML + a closed loader | a security manager can read and argue with it; a typo fails at load, not in an audit |
| Config | pydantic-settings | `SecretStr`, validators, one typed object |
| API | FastAPI + Pydantic v2 | typed responses, OpenAPI for free, read-only by design |
| CLI | Typer + Rich | one command per operation, exit codes 0/1/2/3 |
| Quality | Ruff, mypy, pytest | lint, format, types, 107 tests |
| Delivery | Docker (multi-stage, non-root), GitHub Actions | five jobs including a full end-to-end assessment |

**No LLM.** [ADR-001](docs/decisions.md) explains why at length: a finding that
cannot be reproduced cannot be argued with, and a finding that cannot be argued
with gets ignored.

## Configuration

Everything is environment-driven and validated at startup. The settings worth
knowing:

| Variable | Default | What it changes |
| --- | --- | --- |
| `SENTINEL_ORGANISATION` | Meridian Logistics SAS | printed on every document |
| `SENTINEL_SCOPE` | *(the demo scope)* | the ISMS scope statement — a certificate is granted against a scope, so it appears on every export |
| `SENTINEL_RISK_APPETITE` | 6 | at or below this, a residual risk needs no further treatment |
| `SENTINEL_RISK_ESCALATION` | 15 | at or above this, an acceptance needs top management |
| `SENTINEL_EVIDENCE_MAX_AGE_DAYS` | 365 | a **ceiling** over the catalogue's per-control windows; the stricter applies |
| `SENTINEL_EVIDENCE_WARN_DAYS` | 60 | how early an expiry is reported |
| `SENTINEL_MIN_IMPLEMENTED_RATIO` | 0.95 | the gate's implementation bar |
| `SENTINEL_MAX_CONTROLS_WITHOUT_EVIDENCE` | 0 | how many unevidenced controls the gate tolerates |
| `SENTINEL_REQUIRE_INTERNAL_AUDIT` | true | whether clause 9 is a gate check or a skipped one |
| `SENTINEL_SCHEMA` | isms | validated against `^[a-z_][a-z0-9_]*$` before it reaches SQL |

Every one of the risk and gate numbers is configuration because every one of
them is a business decision someone signs. Each assessment freezes the settings
it ran under, because "ready" under a 50% bar is not the same claim as "ready"
under 95%.

`.env` is git-ignored; the password is a `SecretStr`, so it does not appear in
a traceback or a log line — see [`docs/security.md`](docs/security.md).

## Database setup

```bash
sentinel init-db      # create the schema and its twelve tables; safe to re-run
sentinel reset        # drop it (asks first)
```

Every DDL statement is `CREATE … IF NOT EXISTS`, and a regression test asserts
that re-running initialisation changes no row counts. The reason is specific to
this kind of tool: an evidence index is often the only record that an
organisation ever did the work, and a start-up path that quietly recreates its
tables destroys precisely that.

## Usage

The whole lifecycle, which is also what CI runs:

```bash
sentinel demo --profile gaps    # a simulated ISMS nine months into a programme
sentinel assess                 # every rule and the gate
sentinel findings               # all 44, with remediations
sentinel readiness              # the verdict -> exit code 3
sentinel export                 # SoA, treatment plan, findings, dossier

sentinel demo --profile ready   # the same organisation after remediation
sentinel readiness              # -> exit code 0
```

Inspection: `doctor`, `catalogue`, `controls`, `risks`, `evidence`, `posture`,
`history`. Changing the registers: `accept-risk`, `record-activity`.
One-shot: `cycle`. Serving: `serve`. Everything has `--help`.

Exit codes: `0` success, `1` handled failure, `2` misuse, **`3` refused by the
gate** — a refusal is the tool working, and a nightly pipeline has to be able
to tell it apart from a crash without parsing text.

## The control catalogue

93 Annex A controls and 25 clause requirements, in YAML, loaded through a
closed schema:

```yaml
- id: A.8.13
  title: Information backup
  intent: >-
    Backups are taken according to an agreed policy and -- the part that is
    usually missing -- restored on a schedule to prove they work.
  control_types: [corrective]
  properties: [I, A]
  function: recover
  capability: continuity
  evidence_expected: [record, report]
  evidence_valid_days: 180
```

**It is data, not a table.** What the controls *are* changes with a release;
what the organisation has *done about them* changes every week. One table
holding both cannot distinguish an operator's edit from a revision of the
standard — the exact distinction an audit asks about.

**It is fingerprinted.** A SHA-256 over every catalogue file, recorded on every
assessment. The version is what a human quotes; the fingerprint is what a
machine compares, because two catalogues can carry the same version and
different content. A test proves it: edit one title, leave the version alone,
and the fingerprint changes anyway.

**It contains no text of the standard** — [`docs/catalogue.md`](docs/catalogue.md)
sets out the position in full, and CI checks it twice.

## The risk method

Likelihood × impact, both 1-5, so the scale runs 1-25. Both scores are
generated columns in PostgreSQL, not values the application writes: a risk
score that disagrees with its own factors is the sort of thing nobody notices
until an auditor recalculates one by hand.

**Residual risk counts only implemented controls.** Not planned. Not in
progress. A register where every risk is green because the treatment plan
exists is the most common comfortable fiction in a GRC tool, and here it
produces a finding rather than a score:

```
RSK-026 claims a residual score of 3 (from 10) on control(s) that are not
implemented: A.8.12
```

**An acceptance covers a number, not a risk.** It records the score it was
signed against, so a risk accepted at 4 and re-scored to 8 is reported as
blocking — it carries a signature for a different number. A partial unique
index allows one acceptance in force per risk; re-signing withdraws the
previous one and keeps the row, because "who accepted this, and who changed
their mind" gets asked.

Full method, with the bands and the limits: [`docs/risk-method.md`](docs/risk-method.md).

## Evidence and freshness

An implemented control with no evidence is an assertion, and a certification
audit is an exercise in turning assertions into artefacts.

Each evidence record carries the SHA-256 of the artefact as collected — a
`CHECK` constraint insists it is a real digest, because a "hash" that is not
one looks like proof and is not. The file itself stays wherever the
organisation already keeps documents; this is an index, not a document
management system.

**Freshness is per control.** A malware-protection screenshot is stale after 90
days; an approved policy is not. A single global window is wrong in both
directions at once. `SENTINEL_EVIDENCE_MAX_AGE_DAYS` is a ceiling over the
catalogue's windows and the stricter of the two applies, so a global setting
can tighten and never loosen.

The **newest** artefact decides. Forty stale documents and one collected last
week is an evidenced control; the reverse is not, however impressive the count
looks in a report.

## The finding rules

Twenty-two rules, each a pure function of the snapshot, each naming itself, each
carrying a remediation that the database refuses to let be blank.

| Severity | Meaning |
| --- | --- |
| `blocking` | fails a certification audit on the day — the gate refuses |
| `high` | would very likely become a major nonconformity |
| `medium` | a minor nonconformity or an observation |
| `low` | real, not urgent |
| `info` | worth knowing, not wrong |

The two worth reading the code for:

**`RISK_TREATED_BY_UNIMPLEMENTED_CONTROL`** — the residual score rests on
controls that are not implemented. The number is a forecast, and the tool says
so.

**`ACCEPTANCE_STALE_AFTER_RESCORING`** — the risk was re-scored above what the
acceptance was signed for. Every real register drifts this way, because
re-scoring happens in a quarterly review and acceptances live somewhere else.
Nothing in a spreadsheet notices.

The full reference, and what fires on the demo data:
[`docs/findings.md`](docs/findings.md).

## The readiness gate

Seven checks, each with the number that produced it and the bar it was measured
against:

| Check | Passes when |
| --- | --- |
| `every_control_assessed` | all 93 controls carry an applicability decision |
| `mandatory_clauses_met` | all 22 mandatory clause requirements are met |
| `implementation_ratio` | implemented ÷ applicable ≥ 0.95 |
| `implemented_controls_evidenced` | unevidenced implemented controls ≤ 0 |
| `risks_treated_or_accepted` | nothing above appetite without a covering acceptance |
| `internal_audit_and_review` | both happened, within a year |
| `no_blocking_findings` | the catch-all |

```console
$ sentinel readiness ; echo "exit=$?"
NOT READY every_control_assessed: 92 of 93 controls carry an applicability
decision; 1 do not; mandatory_clauses_met: 19 of 22 ...; implementation_ratio:
83 of 89 applicable controls implemented (93.3%), bar 95%; ...
exit=3
```

**A skipped check is never a pass.** Turning off the clause 9 requirement
records the check as *skipped*, with wording that says it proves nothing — a
gate reporting seven passes when it ran six is a gate nobody should trust.

**`--force` exists and needs a reason.** Forcing without one is itself refused.
The reason is written onto the assessment and printed in the audit dossier
under the verdict, so the exception stays inside the system where the auditor
can see it.

## Documents

`sentinel export` writes four, all deterministic, each hashed and recorded
against the assessment that produced it:

| Document | Read by | Notable |
| --- | --- | --- |
| **Statement of Applicability** (md + csv) | the auditor, first | built by walking the catalogue, so an undecided control appears as **not decided** in the table |
| **Risk treatment plan** | the people doing the work | ordered by inherent risk; flags every acceptance that no longer covers its risk |
| **Findings report** | whoever closes the gaps | grouped by rule, because twelve unevidenced controls are one task with twelve instances |
| **Audit dossier** | the auditor, in order | verdict, position by capability, clause 9 state, blocking findings, then the full SoA |

The justification column is derived where it can be: a control that treats
named risks is included *because* it treats them, and the risk identifiers are
printed. An SoA whose justification reads "best practice" ninety-three times is
a document nobody believes.

Nothing writes a generation timestamp into a document body — determinism is
what makes the hash worth anything. Two exports that differ mean the ISMS
differed.

## The API

```bash
sentinel serve --host 0.0.0.0 --port 8000     # OpenAPI at /docs
```

| Endpoint | Does |
| --- | --- |
| `GET /health` | liveness, database, whether the schema exists |
| `GET /api/v1/catalogue` | version, fingerprint, counts, the copyright position |
| `GET /api/v1/posture` | coverage by theme and capability, risk position, finding counts |
| `GET /api/v1/findings` | the last stored assessment's findings |
| `GET /api/v1/readiness` | **200** when the gate passes, **409** when it refuses |
| `GET /api/v1/risks` | the register, with acceptance status per risk |
| `GET /api/v1/history` | past assessments |

Read-only, deliberately: there is no authentication, and offering "change an
applicability decision" over an unauthenticated endpoint would be an odd thing
for a compliance tool to do. The 409 is the useful part — a monitoring check
can be a URL rather than a parser.

## Testing

```bash
make test               # unit tests, no database
make test-integration   # everything (needs PostgreSQL)
make check              # lint + types + unit tests, which is CI's first job
```

**107 tests**, all passing locally and in CI on Python 3.11 and 3.12.

The unit tests never touch a database, because the rules take everything they
read as an argument. The first assertion in `tests/unit/test_rules.py` is the
one the rest of the file depends on: **a complete ISMS produces no findings at
all.** Every other test breaks exactly one thing and asserts that exactly one
rule fires, so a new rule that misfires on a clean register breaks the suite
immediately.

The ones I would point at in an interview:

- a residual score above its own inherent score is refused *by the database*;
- two acceptances cannot be in force for one risk, and the superseded one is
  kept;
- an exclusion with no justification is refused by a `CHECK`;
- the catalogue fingerprint changes when a control is edited and the version is
  not;
- every defect the demo plants is found, by name;
- the `ready` profile passes all seven gate checks — a gate that has never
  passed is as untrustworthy as one that has never refused;
- **the same registers, 400 days later, stop being ready** — an ISMS decays by
  doing nothing, and that is the property hardest to demonstrate any other way.

No badge in this README claims a coverage percentage, and none claims the tests
pass — the CI badge at the top reports that, honestly.

## Docker

```bash
make up          # PostgreSQL, one assessment run, then the API
make down
docker compose run --rm assess readiness
```

Multi-stage build, non-root user (UID 10001), no secrets baked in, healthcheck
via `sentinel doctor`. The catalogue and the SQL are copied **root-owned**, so
the process that reads the control set cannot edit it — an SoA whose controls
can be changed at run time is an SoA that can be changed without a review. CI
asserts both properties.

The `assess` service exits with the gate's code (3 for the default profile),
and the `api` service depends on `service_started` rather than
`service_completed_successfully` for exactly that reason: the API is most
useful when the answer is "not ready".

> The images have never been built in the environment this project was
> developed in — no Docker daemon was available there. CI builds and
> smoke-tests them on every push.

Five jobs ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)):

| Job | Does |
| --- | --- |
| **lint** | Ruff lint, Ruff format check, mypy |

| **assessment** | the whole lifecycle on both demo profiles |
| **docker** | builds the image, asserts non-root, asserts the catalogue is not writable |

The assessment job does not check that commands exit zero; it asserts the
properties this README claims:

- an ISMS with gaps is refused **with exit code 3**;
- every planted defect is found, by rule name;
- the SoA contains all 93 controls and shows the undecided one as a gap;
- every export is recorded with a 64-character hash;
- forcing without a reason is *still* refused;
- after remediation the same gate passes;
- `/api/v1/readiness` answers 200 for the ready ISMS and 409 once the gaps are
  back.

## Results

Measured on the simulated organisation, seed `20260927`, reference date
2026-09-27. Reproduce with the commands in section 10.

**The organisation.** 22 assets, 28 risks, 93 controls, 25 clause requirements.

| | `gaps` (mid-programme) | `ready` (remediated) |
| --- | --- | --- |
| Controls with a decision | 92 of 93 | 93 of 93 |
| Applicable | 89 | 92 |
| Implemented | 83 (**93.3%**) | 92 (**100%**) |
| Implemented *and currently evidenced* | 79 (95.2%) | 92 (100%) |
| Mean maturity | 3.04 / 5 | 3.18 / 5 |
| Clause requirements met | 21 of 25 | 25 of 25 |
| Risks above appetite | 10 (3 accepted) | 6 (6 accepted) |
| Risk removed by treatment | 43.3% | 54.0% |
| Evidence items | 105 | 129 |

**Findings.**

| Severity | `gaps` | `ready` |
| --- | --- | --- |
| blocking | **11** | 0 |
| high | 23 | 0 |
| medium | 7 | 0 |
| low | 2 | 1 |
| info | 1 | 0 |
| **total** | **44** from 21 rules | **1** |

**The gate.** All seven checks fail on `gaps`; all seven pass on `ready`. The
21 defects planted in `gaps` are listed in [`docs/demo.md`](docs/demo.md), and
both an integration test and a CI step assert that the engine found each kind —
so the demo cannot quietly flatter the engine.

The single finding on `ready` is `EVIDENCE_EXPIRING`: something is due for
renewal in under 60 days. That is the tool being useful rather than the tool
being wrong.

## Limitations

Named, because a compliance project that hides them has failed at the thing it
claims to care about:

- **It checks records, not reality.** An organisation with beautifully
  evidenced controls that nobody operates passes every check here. Only a human
  auditor sampling actual practice catches that — which is what a certification
  audit is for.
- **It does not judge evidence quality.** A screenshot of a policy nobody
  follows counts as a policy.
- **Likelihood and impact are judgement.** There is no frequency data behind
  them. What the tool enforces is that the judgement is recorded, dated, owned
  and re-examined — not that it is right.
- **No identities, so no audit log of who changed what.** `--force` records a
  reason and not a who.
- **No authentication, no secret manager, no signing, no retention policy.**
  All named in [`docs/security.md`](docs/security.md).
- **One organisation per schema.** Multi-tenancy is not modelled.
- **The catalogue is not the standard.** Using this for a real certification
  needs a licensed copy of ISO/IEC 27001 and 27002.

### Future improvements

Authenticated write endpoints with an audit trail; per-control evidence-window
overrides in the database; a second catalogue source so an organisation can map

Vault).

### Security

No credential in the repository, `SecretStr` for the password, `safe_dsn` in
every log line, bound parameters everywhere with an allow-list for the one
thing that cannot be bound, a non-root container that cannot edit its own
catalogue, and an explicit list of what is *not* implemented. Full detail:
[`docs/security.md`](docs/security.md).
