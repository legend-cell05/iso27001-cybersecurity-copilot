# Architecture

> Synthetic data throughout. "Meridian Logistics SAS" is a simulated freight
> company generated by `sentinel demo`; no real organisation, asset, risk or
> evidence artefact exists in this repository, and nothing here has been
> deployed.

The tool answers one question, repeatedly and reproducibly: **would this ISMS
survive a certification audit today, and if not, exactly why?**

---

## 1. The shape of it

```
      catalogue/ (versioned YAML, read-only)            PostgreSQL: schema `isms`
   ┌────────────────────────────────────┐        ┌──────────────────────────────────┐
   │ 93 Annex A controls                │        │ asset                            │
   │ 25 clause requirements (4-10)      │        │ risk + risk_control              │
   │ evidence kinds and freshness rules │        │ risk_acceptance                  │
   │ closed vocabularies                │        │ control_state    ← the SoA       │
   └───────────────┬────────────────────┘        │ requirement_state                │
                   │ fingerprint (SHA-256)       │ evidence                         │
                   │                             │ management_activity              │
                   ▼                             └───────────────┬──────────────────┘
        ┌──────────────────────────────────────────────┐         │
        │           RegisterSnapshot                   │◀────────┘  read once
        │  everything the rules may look at            │
        └───────────────┬──────────────────────────────┘
                        │
        ┌───────────────▼───────────────┐      ┌──────────────────────────┐
        │  22 finding rules             │─────▶│ finding (persisted)      │
        │  pure functions, no queries   │      └──────────────────────────┘
        └───────────────┬───────────────┘
                        │
        ┌───────────────▼───────────────┐      ┌──────────────────────────┐
        │  readiness gate, 7 checks     │─────▶│ assessment + readiness_  │
        │  exit code 3 when refused     │      │ check (persisted)        │
        └───────────────┬───────────────┘      └──────────────────────────┘
                        │
        ┌───────────────▼─────────────────────────────────────────────────┐
        │ exports: Statement of Applicability (md + csv), risk treatment  │
        │ plan, findings report, audit dossier -- each hashed and recorded│
        └─────────────────────────────────────────────────────────────────┘
```

One schema, twelve tables. The schema name is configuration
(`SENTINEL_SCHEMA`) and is validated against `^[a-z_][a-z0-9_]*$` before it is
ever interpolated into SQL, because a schema name cannot be a bound parameter
and the allow-list is therefore the control.

## 2. The snapshot, and why the rules cannot query

Every finding rule is a pure function of one object:

```python
def risk_rules(snapshot: RegisterSnapshot, settings: Settings) -> list[Finding]:
```

`RegisterSnapshot` holds the catalogue, the control decisions, the requirement
states, the risks, the evidence, the computed freshness, the last internal
audit, the last management review, and the date the assessment is being run
for. A rule cannot reach past it.

Three things fall out of that constraint, and they are the reason it is there:

1. **The rules are testable without a database.** The unit suite builds a
   snapshot by hand, breaks exactly one thing, and asserts that exactly one
   rule fires. Rules that are expensive to test are rules nobody adds.
2. **The same rule behaves identically everywhere** — CLI, API, tests. There is
   no code path where the answer depends on how the question was asked.
3. **An assessment is a single consistent read.** Everything is loaded once, so
   a risk cannot be re-scored halfway through an assessment that has already
   judged it.

It also makes `today` an argument rather than a call to `date.today()`, which
is what lets a test assert that an ISMS decays: the same registers, four
hundred days later, stop being ready.

## 3. Layers

| Layer | Module | Responsibility |
| --- | --- | --- |
| Configuration | `config.py` | typed settings, `SecretStr`, schema allow-list, the appetite and gate thresholds |
| Catalogue | `catalogue/loader.py` | load, validate against closed vocabularies, fingerprint |
| Registers | `registers/assets.py`, `risks.py`, `controls.py`, `evidence.py` | what the organisation has recorded |
| Rules | `assessment/rules.py` | 22 finding rules, each naming itself |
| Gate | `assessment/gate.py` | 7 checks, each with its number and its threshold |
| Engine | `assessment/engine.py` | snapshot, totals, persistence, history |
| Exports | `exports/` | SoA, treatment plan, findings, dossier — hashed and recorded |
| Demo | `demo.py` | the simulated organisation, two profiles |
| Orchestration | `pipeline.py`, `cli.py`, `api/app.py` | the operations, and three ways to ask for them |

`pipeline.py` is the only module that composes the others. The CLI contains no
logic: if a command needs a decision made, the decision belongs upstream.

---

## 4. What is enforced by the database

Application code can be bypassed by a second process, an interrupted run or a
manual `UPDATE`. These are constraints instead:

| Property | Mechanism |
| --- | --- |
| A residual risk may not exceed its inherent risk | `CHECK` on `risk` |
| A residual score needs both factors or neither | `CHECK` on `risk` |
| An excluded control carries a written justification | `CHECK` on `control_state` |
| Applicability and status cannot contradict each other | `CHECK` on `control_state` |
| "Implemented" carries a date | `CHECK` on `control_state` |
| At most one acceptance in force per risk | partial unique index |
| An evidence hash is a SHA-256 or nothing | `CHECK` on `evidence` |
| A finding says what to do about it | `CHECK` on `finding` |
| Declaring readiness over a refused gate carries a reason | `CHECK` on `assessment` |

The integration tests assert several of these by trying to violate them.

---

## 5. Idempotent initialisation

Every statement in `sql/schema/` is `CREATE … IF NOT EXISTS`, and a regression
test asserts that re-running initialisation changes no row counts. The reason
is specific to this kind of tool: an evidence index is often the only record
that an organisation ever did the work, and a start-up path that quietly
recreates its tables destroys precisely that.

Dropping is a separate, explicitly named operation that the CLI asks about.

---

## 6. Three ways in, one answer

```
sentinel readiness          → exit 0 ready, exit 3 refused
GET /api/v1/readiness       → 200 ready, 409 refused
pipeline.declare_ready(...) → returns, or raises ReadinessBlocked
```

All three call the same function over the same snapshot. The HTTP status is
part of the contract on purpose: a monitoring check should be able to be a URL
rather than a parser.

## 7. Deliberate limits

- **No LLM anywhere.** A finding that cannot be reproduced cannot be argued
  with, and a finding that cannot be argued with gets ignored. See ADR-001.
- **The API is read-only and unauthenticated.** It reports posture; it does not
  change applicability decisions. See `docs/security.md`.
- **The tool never edits the registers.** It reads them and writes findings. A
  tool that silently fixes its own findings is a tool whose findings mean
  nothing.
- **No evidence storage.** `location` is a path or a URI; the artefact stays in
  whatever document management system the organisation already has.
- **One organisation per database schema.** Multi-tenancy is not modelled.
- **The container images have never been built in this environment** (no Docker
  daemon available); CI builds and smoke-tests them on every push.
